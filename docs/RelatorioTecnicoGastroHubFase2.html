1. Introdução

Descrição do Problema

Na região, um grupo de restaurantes decidiu contratar estudantes para construir um sistema de gestão compartilhado para seus estabelecimentos. A decisão foi motivada pelo alto custo de sistemas individuais, levando os restaurantes a se unirem em torno de uma solução única. Esse sistema permitirá que os clientes escolham restaurantes com base na comida oferecida, em vez de se basearem na qualidade do sistema de gestão.

Objetivo do projeto

O objetivo do projeto é construir o backend do sistema de gestão compartilhado em Spring Boot, contemplando a gestão de tipos de usuários, o cadastro de usuários, o cadastro de restaurantes e o cadastro dos itens do cardápio. Além das funcionalidades, o projeto prioriza práticas de desenvolvimento e estruturação de código limpo: foi organizado em Clean Architecture, com separação clara entre domínio, casos de uso, infraestrutura e apresentação, suporte a documentação via Swagger e testes automatizados.

Nesta fase, o sistema cobre:

  • CRUD de tipos de usuário (UserType), com categorias base CLIENT e OWNER
  • Associação de usuários a um tipo de usuário
  • CRUD de usuários, com garantia de unicidade de e-mail
  • CRUD de restaurantes (nome, endereço, tipo de cozinha, horário de funcionamento e dono)
  • Validação de que o dono do restaurante é um usuário existente e não é da categoria CLIENT
  • CRUD de itens do cardápio (nome, descrição, preço, disponibilidade apenas no local e caminho da foto)
  • Validação de que o item do cardápio pertence a um restaurante existente
  • Estruturação do código em Clean Architecture
  • Documentação via Swagger/OpenAPI
  • Testes automatizados com JUnit 5, Mockito e MockMvc

2. Arquitetura do sistema

Descrição da Arquitetura

O projeto segue os princípios da Clean Architecture, organizado em quatro camadas: domain, application, infrastructure e presentation. As regras de negócio ficam isoladas no domínio e nos casos de uso, que dependem apenas de contratos (interfaces de gateway) — nunca de detalhes de banco de dados ou framework. A comunicação com o banco é feita via Spring Data JPA / Hibernate na camada de infraestrutura, que implementa esses contratos.

Estrutura de Pacotes

br.com.fiap.gastrohubapi
├── domain/                  ← Núcleo do negócio (sem dependência de framework)
│   ├── entity/              ← User, UserType, Restaurant, MenuItem
│   ├── enums/               ← Enumerações: BaseCategory, KitchenType
│   └── exception/           ← Exceções de negócio (ex.: UserTypeInUseException)
├── application/             ← Regras de aplicação
│   ├── gateway/             ← Contratos de persistência (interfaces)
│   └── usecase/             ← user, usertype, restaurant, menuitem
├── infrastructure/          ← Detalhes técnicos
│   ├── config/              ← Registro dos use cases como beans Spring
│   └── persistence/
│       ├── entity/          ← Entidades JPA mapeadas para o banco
│       ├── repository/      ← Repositórios Spring Data JPA
│       └── gateway/         ← Implementações dos gateways (adapters)
└── presentation/            ← Camada HTTP
    ├── controller/          ← REST Controllers com documentação Swagger
    ├── dto/                 ← Request e Response records
    ├── mapper/              ← Conversão domínio ⇄ DTO
    └── exceptionhandler/    ← Handlers globais de erros

Fluxo de Dependências

Presentation ──► Application ──► Domain
Infrastructure ──► Application (implementa os gateways)

A camada de aplicação depende de interfaces de gateway, e não diretamente de implementações de banco. A infraestrutura implementa esses contratos usando JPA, permitindo trocar o mecanismo de persistência sem alterar as regras de negócio.

Associação usuário ⇄ tipo de usuário: conforme solicitado no desafio, o usuário é associado ao tipo de usuário via chave estrangeira user_type_id. Um tipo de usuário em uso não pode ser excluído (regra UserTypeInUseException).

Banco de dados definitivo (produção)

O banco de dados definitivo do projeto é o MySQL 8.4, executado em container Docker definido no docker-compose.yml na raiz do repositório (serviço mysql, imagem oficial mysql:8.4):

services:
  mysql:
    image: mysql:8.4
    container_name: gastrohub-mysql
    environment:
      MYSQL_DATABASE: gastrohub
      MYSQL_USER: gastrohub
      MYSQL_PASSWORD: gastrohub
      MYSQL_ROOT_PASSWORD: root
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql
      - ./sql:/docker-entrypoint-initdb.d:ro,z
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "root", "-proot"]

Características da configuração:

  • Banco: gastrohub, exposto na porta 3306, com usuário dedicado gastrohub.
  • Persistência: os dados são gravados no volume Docker mysql_data, preservados entre reinicializações do container.
  • Carga automática: os scripts sql/01-schema.sql (DDL das tabelas) e sql/02-seed.sql (dados de exemplo) são executados automaticamente pelo container na primeira inicialização, via /docker-entrypoint-initdb.d.
  • Healthcheck: o serviço da API só sobe após o MySQL responder ao mysqladmin ping (condição service_healthy).

No desenvolvimento local e nos testes automatizados, a aplicação utiliza H2 in-memory, dispensando qualquer instalação de banco. O driver MySQL Connector/J está declarado no pom.xml. A configuração completa do Docker é detalhada na seção 7.

5. Tratamento de erros

O tratamento de erros é centralizado em dois handlers globais (@RestControllerAdvice): GlobalExceptionHandler (usuários, restaurantes e itens do cardápio) e UserTypeExceptionHandler (tipos de usuário). As exceções de negócio são lançadas pelo domínio e pelos casos de uso, e convertidas em respostas HTTP com corpo padronizado.

Formato padrão

{
  "timestamp": "2026-07-02T14:00:00Z",
  "status": 404,
  "error": "Not Found",
  "message": "Descrição detalhada do problema"
}

Erros de Validação (400)

Para falhas de Bean Validation (@Valid), o primeiro erro de campo é retornado no formato campo: mensagem:

{
  "timestamp": "2026-07-02T14:00:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "name: Name is required."
}

7. Configuração do Docker

A containerização é composta por um Dockerfile (imagem da API) e um docker-compose.yml (orquestração da API com o banco MySQL), ambos na raiz do repositório.

Dockerfile (multi-stage build)

A imagem da API é construída em dois estágios, gerando uma imagem final enxuta, apenas com o JRE e o JAR da aplicação:

# Build stage
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B clean package -DskipTests

# Run stage
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
  • Estágio de build: usa Maven + JDK 21 para compilar e empacotar o projeto (o cache de dependências é aproveitado ao copiar o pom.xml antes do código).
  • Estágio de execução: usa apenas o JRE 21 (eclipse-temurin:21-jre), reduzindo o tamanho da imagem final.

docker-compose.yml

O Compose define dois serviços:

ServiçoDescrição
mysqlBanco MySQL 8.4 com volume persistente (mysql_data), healthcheck e carga automática dos scripts da pasta sql/ na primeira inicialização (detalhado na seção 3).
apiAplicação GastroHub, construída a partir do Dockerfile, exposta na porta 8080 (configurável via variável API_PORT). Ativa o profile prod (SPRING_PROFILES_ACTIVE), que aponta a conexão para o MySQL através das variáveis de ambiente (DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD), e só inicia após o MySQL estar saudável (depends_on com condition: service_healthy).

Como subir o ambiente

docker compose up --build

O comando constrói a imagem da API, sobe o MySQL (com schema e dados de exemplo) e, em seguida, a API em http://localhost:8080.

8. Qualidade do código

Clean Architecture

  • Domínio independente: as entidades de domínio não possuem anotações JPA nem dependência de framework — a persistência usa entidades JPA próprias, convertidas por métodos fromDomain() / toDomain().
  • Inversão de dependência: os casos de uso dependem de interfaces de gateway (UserGateway, UserTypeGateway, RestaurantGateway, MenuItemGateway); as implementações JPA ficam na infraestrutura.
  • Casos de uso pequenos e focados: cada operação de negócio é um caso de uso próprio (ex.: CreateRestaurantUseCase, DeleteUserTypeUseCase), registrado como bean nas classes de configuração da infraestrutura.

Princípios SOLID Aplicados

  • S (Single Responsibility): cada caso de uso executa uma única operação; controllers tratam apenas o fluxo HTTP; mappers apenas convertem DTOs; validações reutilizáveis são isoladas (ex.: RestaurantDuplicationValidator).
  • O (Open/Closed): novas exceções de negócio podem ser adicionadas aos handlers globais sem alterar os existentes; novos casos de uso não modificam os atuais.
  • L (Liskov Substitution): qualquer implementação de um gateway pode substituir a implementação JPA (por exemplo, um mock nos testes) sem que os casos de uso precisem de ajustes.
  • I (Interface Segregation): cada módulo possui seu próprio gateway com apenas os métodos que utiliza, em vez de uma interface única de persistência.
  • D (Dependency Inversion): a camada de aplicação depende de abstrações (gateways), nunca de repositórios JPA concretos.

Outras Boas Práticas

  • Entidades autovalidadas: factory methods create() / restore() impedem a construção de objetos em estado inválido.
  • DTOs imutáveis: requests e responses implementados como Java record, separados por operação.
  • Validação na entrada: @Valid + Bean Validation (@NotBlank, @NotNull, @Email, @DecimalMin) nos DTOs de request.
  • Senha nunca exposta: o campo password não existe no DTO de response de usuário.
  • Erros padronizados: corpo de erro consistente em toda a API (timestamp, status, error, message).
  • Fetch LAZY: a associação usuário → tipo de usuário usa FetchType.LAZY, evitando consultas desnecessárias (problema N+1).
  • Documentação viva: anotações OpenAPI mantidas junto aos controllers.

12. Guia passo a passo para testar o projeto

Este guia reúne tudo que é necessário para clonar, subir e testar o projeto do zero pelo Swagger UI.

Pré-requisitos: para executar com containers, apenas Docker (com o plugin Compose). Para executar localmente sem Docker, apenas Java 21 (JDK) — o projeto usa o Maven Wrapper, portanto não é necessário instalar o Maven.

Etapa 1: Clonar o repositório

Abra o terminal (Prompt de Comando, PowerShell ou Terminal do Mac/Linux) e execute:

git clone https://github.com/GastroHubDev/gastrohub-api.git
cd gastrohub-api

Etapa 2: Subir a aplicação

Opção A: Com Docker (API + MySQL)

Na pasta do projeto, execute:

docker compose up --build

O Compose constrói a imagem da API e sobe o container MySQL 8.4 com o schema e os dados de exemplo carregados automaticamente (seção 7).

Opção B: Execução local (H2 in-memory)

Sem Docker, execute com o Maven Wrapper:

# Linux / macOS
./mvnw spring-boot:run

# Windows
.\mvnw.cmd spring-boot:run

Nesta opção a aplicação usa o banco H2 in-memory, criado automaticamente pelo Hibernate — nenhuma configuração de banco é necessária.

Em ambas as opções, a aplicação iniciará em http://localhost:8080.

Etapa 3: Testar pelo Swagger UI

3.1: Acessar o Swagger

http://localhost:8080/swagger-ui.html

A página exibirá todos os endpoints documentados da API, agrupados pelas tags User Types, Users, Restaurants e Menu Items.

3.2: Criar um tipo de usuário

  1. Clique em POST /user-types
  2. Clique no botão "Try it out"
  3. Substitua o corpo de exemplo pelo JSON abaixo e clique em "Execute":
{
  "name": "Dono de Restaurante",
  "baseCategory": "OWNER"
}

A resposta esperada é 201 Created. Copie o id (UUID) retornado para o próximo passo.

3.3: Criar um usuário dono de restaurante

Em POST /users, informe o tipo criado no passo anterior:

{
  "name": "Maria Oliveira",
  "email": "maria.oliveira@email.com",
  "password": "senha123",
  "userTypeId": "<UUID copiado no passo 3.2>"
}

A resposta será 201 Created com o id (UUID) do usuário. Copie esse UUID para o próximo passo.

3.4: Criar um restaurante

Em POST /restaurants, use o UUID do usuário como restaurantOwnerId:

{
  "name": "Cantina da Nonna",
  "address": "Av. Paulista, 1000 - São Paulo/SP",
  "kitchenType": "ITALIAN",
  "openingHours": "Seg a Dom, das 11h às 23h",
  "restaurantOwnerId": "<UUID copiado no passo 3.3>"
}

A resposta será 201 Created. Copie o UUID do restaurante.

3.5: Criar um item do cardápio

Em POST /menu-items, use o UUID do restaurante:

{
  "name": "Lasanha à Bolonhesa",
  "description": "Massa fresca com molho bolonhesa e queijo gratinado",
  "price": 59.90,
  "onlyInRestaurant": false,
  "photoPath": "/images/pratos/lasanha-bolonhesa.png",
  "restaurantId": "<UUID copiado no passo 3.4>"
}

3.6: Explorar os demais endpoints

  • GET /restaurants: lista todos os restaurantes
  • GET /menu-items/restaurant/{restaurantId}: lista o cardápio do restaurante
  • GET /users/search?name=Maria: busca usuários pelo nome
  • PUT e DELETE nos módulos para atualizar/excluir registros
  • Teste os cenários de erro: criar restaurante com dono CLIENT (400), excluir tipo de usuário em uso (409), buscar ID inexistente (404)

3.7: Inspecionar o banco (opcional)

Na execução local (Opção B), o console do H2 está habilitado em:

http://localhost:8080/h2-console

JDBC URL:  jdbc:h2:mem:gastrohub
User:      sa
Senha:     (em branco)

Etapa 4: Executar os testes automatizados

# Linux / macOS
./mvnw test

# Windows
.\mvnw.cmd test
Observação: na execução local com H2 (Opção B), o banco é in-memory e os dados são perdidos ao reiniciar a aplicação — repita as etapas 3.2 a 3.5 após cada reinício.

13. Observações e Limitações conhecidas

Esta seção documenta limitações identificadas durante o desenvolvimento e os testes da Fase 2, que estão fora do escopo atual ou serão tratadas antes da entrega final.

Banco H2 na execução local

O banco definitivo de produção é o MySQL em container (seções 3 e 7): no ambiente Docker, o Compose ativa o profile prod (application-prod.properties), que parametriza a conexão pelas variáveis de ambiente DB_HOST, DB_PORT, DB_NAME, DB_USER e DB_PASSWORD. Na execução local de desenvolvimento e nos testes automatizados, a aplicação utiliza H2 in-memory, cujos dados são perdidos a cada reinício.

Ausência de autenticação

Nesta versão não há camada de segurança: todos os endpoints são públicos.

Senha armazenada sem hash

A senha do usuário é validada como obrigatória e nunca retornada nas respostas, porém ainda é persistida sem algoritmo de hash. O hashing poderá ser incorporado em evolução futura, junto com uma camada de autenticação.

Ausência de paginação

Os endpoints de listagem (GET /users, GET /restaurants, GET /menu-items etc.) retornam todos os registros sem paginação. Em fases futuras será implementada a paginação com Pageable.

Relacionamentos por referência de ID

As associações restaurante → dono e item do cardápio → restaurante são mantidas por UUID (validado nos casos de uso), sem chave estrangeira física no banco. A integridade referencial é garantida em nível de aplicação.
